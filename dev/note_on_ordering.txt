   is it a problem that we don't preserve order of elements in slicee


• Yes—if profile values can be decoded and serialized again, losing slice order is a real problem.

  The current generated representation splits one ordered JSON array into separate fields:

  diastolic: UsCoreBloodPressureComponentDiastolic,
  systolic: UsCoreBloodPressureComponentSystolic,
  component: List(UsCoreBloodPressureComponent),

  See gleam-fhir/src/fhir/r4us/resources.gleam:120355. Given:

  "component": [other1, systolic, other2, diastolic]

  we retain each value but lose that interleaving. Re-encoding by concatenating the fields would reorder the array, contrary to FHIR’s requirement that array order be
  maintained. FHIR R4 JSON representation (https://hl7.org/fhir/R4/json.html#2.6.2.1)

  Also, slicing.ordered = false does not make this safe. It means instances need not arrange slice categories in profile-definition order; it does not authorize a
  parser to reorder the received array. ElementDefinition.slicing.ordered
  (https://hl7.org/fhir/R4/elementdefinition-definitions.html#ElementDefinition.slicing.ordered)

  I’d make the wire-preserving representation an ordered sum-type list:

  pub type UsCoreBloodPressureComponentSlice {
    Systolic(UsCoreBloodPressureComponentSystolic)
    Diastolic(UsCoreBloodPressureComponentDiastolic)
    Other(UsCoreBloodPressureComponent)
  }

  component: List(UsCoreBloodPressureComponentSlice)

  The decoder or a smart constructor would then validate slice cardinalities—exactly one systolic and one diastolic—at runtime. That trades some compile-time
  cardinality enforcement for correct, lossless FHIR representation.

  If keeping separate required fields is important, we would need an additional canonical ordering structure or retain the base Observation; merely keeping three
  buckets is insufficient.

  So:

  - Parse-only, lossy profile view: current design can be acceptable if explicitly documented.
  - Parse/edit/serialize FHIR model: we should change it.
  - This affects slicing of repeating elements; slicing a non-repeating choice element does not have this particular problem.

• Yes. Between those options, I’d prefer one canonical ordered component list plus generated getter/setter functions.

  Recording positions alongside separate fields creates two representations of the same information:

  systolic: Systolic
  systolic_position: Int
  diastolic: Diastolic
  diastolic_position: Int
  component: List(Component)

  That introduces consistency problems whenever an item is inserted, removed, or moved. Positions shift, can collide, and must be validated before serialization.

  Instead:

  component: List(UsCoreBloodPressureComponent)

  with generated functions conceptually like:

  pub fn us_core_blood_pressure_get_systolic(
    observation: UsCoreBloodPressure,
  ) -> Result(UsCoreBloodPressureComponent, SliceError)

  pub fn us_core_blood_pressure_set_systolic(
    observation: UsCoreBloodPressure,
    systolic: UsCoreBloodPressureComponent,
  ) -> Result(UsCoreBloodPressure, SliceError)

  The getter finds the element using the slice discriminator. The setter replaces it at its existing position, preserving the rest of the array exactly. If absent and
  allowed to add it, it inserts according to slicing.ordered rules or a documented default.

  I would still consider retaining the generated Systolic and Diastolic types, just not storing them as separate top-level fields:

  pub fn get_systolic(
    observation: UsCoreBloodPressure,
  ) -> Result(UsCoreBloodPressureComponentSystolic, SliceError)

  pub fn set_systolic(
    observation: UsCoreBloodPressure,
    value: UsCoreBloodPressureComponentSystolic,
  ) -> UsCoreBloodPressure

  That gives us both:

  - One authoritative ordered list for lossless FHIR serialization.
  - Narrowed slice types for profile-specific cardinality and value constraints.

  The tradeoff is that required slice cardinality is no longer obvious directly from the top-level constructor. We can enforce that in the profile decoder/validated
  constructor. I think that is cleaner than making position metadata part of every sliced resource.

   and then List2(UsCoreAverageBloodPressureComponent) would that be better in terms of preserving order? with fns to get/set


• Yes, that would preserve order much better because the JSON array maps directly to one Gleam list. List2 also correctly expresses the total component minimum of
  two.

  I would structure it with payload types rather than duplicating all fields inside the sum type:

  pub type UsCoreAverageBloodPressureComponent {
    Systolic(UsCoreAverageBloodPressureComponentSystolic)
    Diastolic(UsCoreAverageBloodPressureComponentDiastolic)
    Other(UsCoreAverageBloodPressureComponentOther)
  }

  pub type UsCoreAverageBloodPressure {
    UsCoreAverageBloodPressure(
      component: List2(UsCoreAverageBloodPressureComponent),
      // ...
    )
  }

  This has a few advantages:

  - List order is exactly JSON array order.
  - set_systolic can replace the existing variant in place.
  - get_systolic can return the narrowed systolic type.
  - Slice-specific constraints remain represented by distinct Gleam types.
  - Other can still enforce the common profile constraints on component, rather than falling all the way back to the unrestricted base ObservationComponent.

  For example:

  pub fn get_systolic(
    blood_pressure: UsCoreAverageBloodPressure,
  ) -> Result(
    UsCoreAverageBloodPressureComponentSystolic,
    SliceCardinalityError,
  )

  pub fn set_systolic(
    blood_pressure: UsCoreAverageBloodPressure,
    systolic: UsCoreAverageBloodPressureComponentSystolic,
  ) -> Result(UsCoreAverageBloodPressure, SliceCardinalityError)

  set_systolic scans the list and replaces:

  Systolic(_) -> Systolic(systolic)

  at the same position. Everything else stays untouched.

  One important limitation: List2 proves only that there are at least two components. It does not prove that there is exactly one Systolic and exactly one Diastolic;
  this would also satisfy List2:

  list2.new(Other(a), Other(b))

  So the profile decoder/validated constructor must still enforce slice cardinalities. Once the value has been validated, getters could return the required value
  directly instead of Result—especially if the profile type is opaque.

  The decoder should classify by discriminator first:

  - Systolic discriminator → decode as Systolic; failure is an error.
  - Diastolic discriminator → decode as Diastolic; failure is an error.
  - No discriminator match → Other for open slicing, or error for closed slicing.

  It must not fall back to Other when something identifies as systolic but violates the systolic constraints.

  So yes: ordered List2 of slice variants is the strongest design discussed so far. I’d only change the inline variants to wrapped slice types, mainly so the
  generated getter/setter APIs remain strongly typed.


› the thing with calling it Systolic Diastolic Other is without what if name collides? also why not write fields directly inside the sum type? for one thing the

• You’re right about both pressures: short variant names are unsafe in this generated mega-module, and directly embedding fields is a legitimate simplification. The
  deciding tradeoff is whether the API needs a statically typed “systolic value” independent of the enclosing sum type, plus whether the unsliced component has
  profile-wide constraints beyond base Observation.component.

• You can write the fields directly inside the sum type. It preserves order just as well as wrapping separate slice types, and produces fewer generated types.

  Short constructors such as Systolic would collide because Gleam constructors share the module namespace. Since all generated resources live together, the fully
  prefixed names from your example are appropriate:

  pub type UsCoreAverageBloodPressureComponent {
    UsCoreAverageBloodPressureComponentSystolic(
      // narrowed fields
    )

    UsCoreAverageBloodPressureComponentDiastolic(
      // narrowed fields
    )

    UsCoreAverageBloodPressureComponentOther(
      component: ObservationComponent,
    )
  }

  I would call the final constructor ...Other or ...Unmatched, rather than giving it the same name as the type.

  The only reason to use wrapped slice types is getter/setter typing. With inline fields, a systolic variant is not its own type; every variant has type
  UsCoreAverageBloodPressureComponent. Therefore:

  get_systolic(bp)
    -> Result(UsCoreAverageBloodPressureComponent, SliceError)

  cannot express in its return type that the result is definitely the systolic constructor. Likewise, this signature permits passing a diastolic value:

  set_systolic(
    bp,
    component: UsCoreAverageBloodPressureComponent,
  )

  The function would need to check the constructor and return an error. That may be an entirely acceptable tradeoff for avoiding lots of wrapper types.

  And yes, the other case can reuse ordinary ObservationComponent when the profile places no common restrictions on all components. Code generation should choose:

  UsCoreAverageBloodPressureComponentOther(ObservationComponent)

  when the unsliced Observation.component definition is unchanged.

  In the general case, however, the slicing entry can constrain fields common to every component, including unmatched elements. Then the other variant needs a
  generated constrained type:

  UsCoreAverageBloodPressureComponentOther(
    UsCoreAverageBloodPressureComponentUnmatched,
  )

  So my recommendation is essentially your design:

  component: List2(UsCoreAverageBloodPressureComponent)

  with fully prefixed inline variants, reusing ObservationComponent whenever there are no profile-wide component restrictions. The decoder validates exactly one
  systolic and one diastolic, while setters replace the relevant variant in place. The wrapper types are optional API strictness, not necessary for order
  preservation.

• That exposes the fundamental tradeoff. With only:

  components: List2(Component)

  the type system guarantees at least two elements, but not that one is systolic. Therefore a total get_systolic -> Systolic cannot be implemented from that
  representation without one of:

  - Returning Result.
  - Asserting/panicking on the impossible branch.
  - Storing the guaranteed systolic structurally.

  If library assertions are off the table, I would return to separate slice fields—but preserve order with a layout list rather than integer positions:

  pub opaque type UsCoreAverageBloodPressureComponents {
    UsCoreAverageBloodPressureComponents(
      systolic: UsCoreAverageBloodPressureComponentSystolic,
      diastolic: UsCoreAverageBloodPressureComponentDiastolic,
      layout: List2(UsCoreAverageBloodPressureComponentLayout),
    )
  }

  type UsCoreAverageBloodPressureComponentLayout {
    UsCoreAverageBloodPressureComponentSystolicPosition
    UsCoreAverageBloodPressureComponentDiastolicPosition
    UsCoreAverageBloodPressureComponentOther(ObservationComponent)
  }

  An original array such as:

  [other1, systolic, other2, diastolic]

  becomes:

  systolic: <systolic value>
  diastolic: <diastolic value>
  layout: [
    Other(other1),
    SystolicPosition,
    Other(other2),
    DiastolicPosition,
  ]

  Then the getter is genuinely total:

  pub fn get_systolic(
    components: UsCoreAverageBloodPressureComponents,
  ) -> UsCoreAverageBloodPressureComponentSystolic {
    let UsCoreAverageBloodPressureComponents(systolic:, ..) = components
    systolic
  }

  And set_systolic only replaces the stored field; its position remains unchanged. Serialization traverses layout, substituting the stored required values at their
  markers.

  The type needs to be opaque. Its decoder and public constructors validate that the layout contains exactly one systolic marker and one diastolic marker. After
  construction, generated setters maintain that invariant.

  So there is a three-way constraint:

  1. One plain ordered list.
  2. A non-failing, specifically typed getter.
  3. No assertion or partial operation.

  We cannot have all three because Gleam cannot express “this list contains exactly one constructor X.” The layout-plus-fields representation squares it cleanly:
  ordered representation, total accessors, and no assertion. It is effectively “record the positions,” but symbolic position markers are safer than integer indexes
  because unrelated insertions do not require recalculating indexes.
